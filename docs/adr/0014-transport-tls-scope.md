# ADR-0014: TLS on the node's HTTP listener — real, working, opt-in, trust-on-first-use; cross-platform client trust is a documented gap, not attempted here

**Status:** Accepted
**Date:** 2026-08-06

## Context

Issue #49 asks whether the HTTP transport is encrypted (it was not, before this batch — plain `node:http`) and directs: attempt real TLS first; a self-signed certificate is acceptable for a local-network node; document the trust model (e.g. trust-on-first-use / cert pinning) rather than a full PKI; if full TLS is genuinely too large a lift, an acceptable fallback is documenting the gap with message-level signing as the interim mitigation — but real TLS should be attempted first.

Two concrete constraints shape what's actually achievable here:

1. **Node has no built-in X.509 certificate _issuance_ API.** `node:crypto`/`node:tls` can generate keypairs and _terminate_ TLS given a certificate, but minting a self-signed certificate needs either an external library or shelling out to a CLI tool.
2. **`HttpTransportClient` (`adapters/transport-http`) is shared across every client target** — mobile native, mobile web, and (via this same package) potentially a future node-to-node client — via plain `fetch`. Browsers and React Native's `fetch` implementations do not expose a way to pin a self-signed certificate's fingerprint the way `node:https.request`'s `ca`/`checkServerIdentity` options do. A self-signed certificate presented to a stock `fetch` call is simply rejected as untrusted, with no in-code override available (unlike a real CA-issued certificate, which does not exist for a private LAN node and would be disproportionate machinery to stand up for one deployment).

## Decision

**Real TLS, fully working on the server side, opt-in and defaulting off.**

1. **Certificate issuance via the system `openssl` binary** (`clients/node/src/composition/tls-cert.ts`), verified present on both of SPEC.md §9's target platforms (Linux, macOS ship it by default or via first-party developer tooling). This is the one dependency-free, universally-available way to actually mint a certificate — chosen over adding an npm dependency (e.g. `node-forge`, `selfsigned`) because a single, well-audited system tool that operators already trust for every other TLS deployment on their machine is a smaller trust surface than a new JS dependency doing ASN.1 encoding, and because `openssl` is already a reasonable assumption for "a Linux/macOS server operator's toolchain," unlike an arbitrary npm package.
2. **Generated once, persisted, reused across restarts** (`<identityStorageDir>/tls/{cert.pem,key.pem}`) — a node's TLS identity is as stable as the machine it runs on, exactly like SPEC.md §7's "nodes have persistent identities."
3. **Trust-on-first-use (TOFU), pinned by fingerprint — not a CA.** There is no certificate authority a self-signed local-network node's certificate could meaningfully chain to; standing up a private CA for a single-node (or even multi-node) deployment is disproportionate machinery for what SPEC.md §4 describes (a machine on a Wi-Fi network at one venue). The trust model this actually achieves is the same one SSH host keys use: a client that connects and pins the certificate's fingerprint the first time is protected against a _subsequent_ man-in-the-middle, with the well-known caveat that the _very first_ connection is only as trustworthy as the channel the fingerprint was learned over.
4. **`HttpTransportServer` gained a `tls` constructor option** (`adapters/transport-http/src/http-transport-server.ts`) that switches the underlying listener from `node:http` to `node:https` — proven with a real TLS handshake test (`http-transport-server-security.test.ts`, using `node:https.request` with the certificate explicitly supplied as `ca`, not with verification disabled) and a real end-to-end test through `clients/node`'s actual certificate-generation path (`tls-cert.test.ts`).
5. **Opt-in, `config.tlsEnabled` defaulting to `false`.** This is the one security control in this batch that is _not_ unconditionally on (contrast ADR-0013's authentication, which always is), because turning it on by default would break every existing `fetch`-based swap client (mobile, web, and this same test suite's own e2e test) against a self-signed certificate they cannot verify — an operator who wants TLS today can enable it, but must additionally arrange client-side trust out of band (e.g. importing the certificate into an OS trust store for a Node-based client, or accepting that browser/RN clients cannot swap with this node until a real cross-platform trust mechanism exists — see "Consequences").

## Alternatives considered and rejected

- **Skip TLS entirely; document the gap and rely on message-level signing as the sole mitigation** (the brief's own stated fallback). Rejected as the _primary_ answer, per the brief's explicit instruction to attempt real TLS first — and it turned out to be achievable on the server side within this batch's scope. Retained as accurate framing for the _residual_, client-side half of the gap (see Consequences) rather than the whole story.
- **A full PKI (a private certificate authority operators provision, distribute, and trust).** Rejected: SPEC.md's node is a single machine at one venue, not a fleet needing centralized certificate management — a CA is solving a coordination problem this deployment shape does not have, at real operational cost (key ceremony, distribution, revocation) for zero benefit over a directly-pinned fingerprint.
- **`NODE_TLS_REJECT_UNAUTHORIZED=0` (globally disabling certificate verification) as a shortcut to let `fetch` accept a self-signed cert.** Rejected outright: this is a process-wide flag that disables certificate verification for _every_ outbound HTTPS request the process makes, not just this one connection — a blunt, dangerous instrument that trades one gap for a much larger one (every other HTTPS call in the process becomes MITM-able too). None of this batch's code sets it, and it should not be reached for in a future batch either.
- **Add an npm dependency for pure-JS certificate generation (e.g. `selfsigned`, `node-forge`) instead of shelling out to `openssl`.** Rejected for this batch: `openssl` achieves the identical outcome with zero new supply-chain surface, on the exact platforms this project targets (SPEC.md §9). Revisit only if a target platform without a usable `openssl` binary becomes a real requirement (e.g. a constrained embedded deployment), which is not on this project's current roadmap.
- **Reusing the node's Ed25519 _identity_ signing key (the same one that signs content and the authentication handshake) as the TLS certificate's key, rather than generating an independent TLS keypair.** Considered, but kept separate: `openssl req -x509` with an Ed25519 key is achievable, but conflating "the key that signs application-level content and proves identity in the handshake" with "the key that terminates TLS" means any future TLS key rotation policy (e.g. shorter-lived certs than an application identity should have) is entangled with identity rotation policy, and vice versa. A dedicated EC (P-256) TLS keypair, generated and persisted independently under the same `identityStorageDir`, keeps the two concerns — and their respective rotation lifecycles — decoupled, at the cost of one extra keypair on disk.

## Consequences

- **What is real and working today:** a node can serve HTTPS with a genuine, verifiable, persistent self-signed certificate; a client that knows to pin that certificate's fingerprint (or, as tested, is handed the exact PEM to trust via `ca`) gets real confidentiality and a real MITM defense on subsequent connections.
- **What remains a genuine, undischarged gap:** the cross-platform swap client (`HttpTransportClient`, used by the browser and React Native targets) has no code path today to pin a self-signed certificate's fingerprint the way a real TOFU implementation needs — browser `fetch` and RN's networking stack manage their own trust stores with no JS-level override for this case. Concretely, this means: with `tlsEnabled: true`, a phone or browser client cannot complete a swap with that node today without an operator separately getting that certificate into the OS/browser trust store (a real, if clunky, workaround) or a future batch adding a platform-specific pinning UX (e.g. RN: a native module wrapping the platform's own certificate-pinning API; browser: none exists — a browser fundamentally cannot pin an arbitrary certificate via JS, which may mean a public swap node ultimately needs a real CA-issued certificate via something like Let's Encrypt if it is ever exposed beyond a trusted LAN, a bridge to cross only if that deployment shape becomes real).
- **This is why `tlsEnabled` defaults to `false`:** turning it on does not yet deliver a working swap experience for the majority of this project's client targets, so it is not the default, but it is fully available, tested, and correct for the deployment shapes that can already use it (a Node-based client with `HttpTransportClient` extended to pin a fingerprint — a small, concrete follow-up now that the server half exists — or an operator-arranged trust store).
- **Threat model impact:** `docs/security/threat-model.md` §3.7 tracks transport confidentiality as the single largest deliberately-scoped-out gap in this batch, with this ADR as the pointer to exactly what would close it.
